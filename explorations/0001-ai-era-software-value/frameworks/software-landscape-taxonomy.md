# 软件产业分类图谱（Software Landscape Taxonomy）

**所属探索**：Exploration 0001 — AI 时代软件价值的初步研究  
**阶段**：阶段 1 - 发现与理解  
**创建日期**：2026-11-10  
**最后更新**：2026-11-10（引入 Security, Assurance & Trust 横切研究主题，见第 3 节）  
**本文档目的**：建立软件产业的结构化地图，作为后续「AI 影响叠加分析」（Step 2）和「机会识别」（Step 3）的基础坐标系。

---

## 0. 为什么需要这张图谱

现有探索已有的证据大多来自**顶层视角**（EY-Parthenon、Gartner、CMA、OECD 四份宏观报告）和**点状案例**（花叔的三个项目），但缺少一张**中间层的结构地图**。

没有这张地图，我们会面临三个问题：

1. Gartner 对 agentic arbitrage 影响企业应用软件支出的预测，具体涉及哪些品类？
2. VISION.md 说"壁垒从代码转向工作流/数据/集成/信任"，但这个转变在**不同品类**里的表现差异巨大。
3. 现有 5 个产品假设（HYP-001~005）散布在地图的哪些区域？**有没有遗漏的高价值区域**？

本图谱不回答"AI 如何改变软件"——那是 Step 2 的工作。本图谱只回答"**软件到底由哪些类别构成，每一类现在是什么样子**"。先有地形的准确描述，才能讨论风怎么吹。

## 1. 研究分类框架：多维观察标签，不是 MECE 市场分区

这份图谱是用于发现研究问题的**多维索引**，不是互斥且穷尽的产业统计分类。一个产品可以承担多个功能角色，也可能横跨行业、用户场景和交付形态。

### 轴 A：产品功能与价值角色

描述产品主要帮助用户完成什么工作。类别 1–7 和类别 10 主要属于这一维度；类别 8（垂直行业）与类别 9（个人/家庭场景）是横切标签，不应与其他类别视为同一层级的市场分区。

分类时记录一个**主要观察标签**和零个或多个**次要标签**。主要标签依据产品当前最核心、最频繁或最具差异化的用户任务确定；若证据不足，标记为“待判定”，不要为了填表强行归类。

### 轴 B：购买者、使用者与组织情境

不要把交易关系、组织规模和用户角色混为一个字段。分别记录：
- **购买者/付费者**：个人、企业、政府、非营利机构等。
- **实际使用者**：员工、管理者、开发者、家庭成员、专业人员等。
- **组织规模/情境**：个人、微型/小型/中型/大型组织、家庭、公共服务场景等。

同一产品可能有不同的购买者和使用者；这些字段允许多值。

### 轴 C：交付形态（可组合）

记录产品通过哪些组成部分交付，而不是强制单选：
- **应用**：Web / Mobile / Desktop GUI
- **服务**：API / SaaS 后端能力
- **知识资产**：Skill / 知识库 / 可加载的认知结构
- **工作流**：Agent 能力 / 可执行流程

一个产品可以同时包含以上多种形态。

### 轴 D：AI 影响分析以任务为单位

不要给整个产品贴上单一的 AI-native、AI-augmented、AI-substitutable 或 AI-resistant 标签。Step 2 应拆解具体任务，分别评估：
1. AI 对该任务是自动执行、辅助判断，还是基本没有影响？
2. 自动化后仍需哪些人工判断、授权和责任承担？
3. 在目标环境中，准确性、稳定性和可复核性达到什么程度？
4. 任务发生变化后，用户工作流、成本和购买决策是否真的改变？

产品层面的判断只能由其内部任务分析汇总得出，不可反过来代替任务证据。

### 轴 E：Security, Assurance & Trust（安全、保障与可信）

横切研究主题，不是第 11 个功能类别。安全在软件产业中有双重身份：它本身是庞大的软件产品产业（主要落在类别 7 的观察标签上），同时是贯穿所有软件类别的底层技术维度——一个财务软件、一个 AI Agent、一个操作系统、一套数据库，都有自己的安全问题。

给产品打标签时，除轴 A–D 外可记录：该产品处于哪些**信任边界**上（用户/Agent/工具/系统/第三方服务）、依赖哪些**保障方法**（证明/分析/测试/审计/来源验证）。

主题的完整展开（三层技术分支、七个可信基础、信任链、AI Agent 时代延伸问题、已核实的研究基础框架）见第 3 节。

## 2. 十类观察标签（允许交叉）

每个类别包含：定义、代表产品、核心价值、当前商业模式、典型壁垒、Step 2 待研究问题。

> 代表产品用于说明类别边界，不代表市场份额、市场领导地位或用户偏好。本图谱不估算市场规模、不进行星级排序，也不比较类别大小。若后续需要市场测算，必须另行定义地域、年份、收入范围、统计对象和类别边界，并说明交叉部分；不同类别的估值不得直接相加。

### 类别 1：系统记录型（System of Record）

- **定义**：作为组织"单一事实来源"的数据存储与管理系统，核心是结构化数据的录入、存储、查询与追溯。
- **代表产品**：ERP（SAP、Oracle ERP、用友、金蝶）、CRM（Salesforce、HubSpot、销售易）、HRIS（Workday、北森）、财务/会计（QuickBooks、金蝶精斗云）、通用数据库应用。
- **核心价值**：让组织的数据有秩序、可追溯、可共享；是其他所有系统的数据底座。
- **当前商业模式**：按席位（per-seat）SaaS 订阅为主，大型企业常含实施服务费与定制开发。
- **典型壁垒**：数据迁移成本极高（锁定效应）、流程深度嵌入组织、合规与审计要求。
- **Step 2 待研究**：Agent 能否绕开 UI 直接读写这些系统，使"记录"本身被架空？壁垒中的哪一项（迁移成本/合规/流程嵌入）在 AI 时代依然成立？

### 类别 2：流程自动化型（Workflow & Process Automation）

- **定义**：减少人工步骤、把分散系统连起来、按规则自动执行任务的中间层。
- **代表产品**：RPA（UiPath、Automation Anywhere）、iPaaS/集成（Zapier、Make、钉钉连接器）、BPM/工作流引擎、CI/CD（Jenkins、GitLab CI）、低代码/无代码（Airtable、明道云、简道云）。
- **核心价值**：把"人在多个系统间搬运数据、重复点击"变成自动流转。
- **当前商业模式**：按任务执行量（usage）、按席位、平台授权。
- **典型壁垒**：连接器生态广度、与现有系统的集成深度、配置门槛。
- **Step 2 待研究**：这类软件**最接近被 Agent 直接吞掉**——它本身就是"自动化"，AI Agent 是更通用的自动化。Gartner 的 "$234B 冲击"主要落在这里吗？

### 类别 3：沟通协作型（Communication & Collaboration）

- **定义**：人与人之间信息同步、讨论、共创的载体。
- **代表产品**：即时通讯（Slack、Teams、飞书、企业微信）、文档协作（Notion、Confluence、腾讯文档）、视频会议（Zoom、腾讯会议）、项目管理（Asana、Jira、Trello）、邮箱。
- **核心价值**：降低协作摩擦，让团队"在同一页上"。
- **当前商业模式**：按席位 SaaS，常捆绑办公套件。
- **典型壁垒**：网络效应（全员都在用才有效）、习惯锁定。
- **Step 2 待研究**：AI 摘要/起草已嵌入，但"人-人沟通"本身难以被替代；可被增强的是会议记录、信息检索、跨工具同步（恰好对应 HYP-002 Family OS 的部分诉求）。

### 类别 4：专业创作/生产工具型（Professional Creation & Production）

- **定义**：专业人士用以产出专业成果的创作与生产工具。
- **代表产品**：设计（Figma、Photoshop、创客贴）、开发（IDE、GitHub、Cursor）、3D/CAD（AutoCAD、Blender、SolidWorks）、音视频编辑（Premiere、剪映）、写作/排版工具。
- **核心价值**：放大专家的能力，把专业产出门槛降低。
- **当前商业模式**：按席位订阅、一次性授权、部分按产出计费。
- **典型壁垒**：专业工作流深度、格式与生态兼容性、专家习惯。
- **Step 2 待研究**：这是 AI 渗透**最深也最争议**的类别（花叔的 Huashu Design 即此领域）。AI 是"替代新手"还是"增强专家"？哪些子类的壁垒会被击穿？

### 类别 5：决策支持/智能分析型（Decision Support & Analytics）

- **定义**：把数据转化为可行动判断的系统。
- **代表产品**：BI（Tableau、PowerBI、帆软）、数据分析、预测与 forecasting、风控/评分、推荐引擎、A/B 实验平台。
- **核心价值**：辅助人或系统做出更好的决策。
- **当前商业模式**：按席位、按数据量/查询量。
- **典型壁垒**：数据接入广度和质量、领域模型准确性、信任。
- **Step 2 待研究**：这类软件**天然与 AI 同源**——它的核心价值"辅助判断"正是 LLM 的强项。是会被 AI 平台吸收，还是借 AI 升级？信任与可解释性是关键变量（呼应 CMA 监管报告）。

### 类别 6：内容/媒体/消费型（Content, Media & Consumer）

- **定义**：面向终端消费者的内容消费、娱乐、社交与互动。
- **代表产品**：游戏、社交媒体（微信、抖音、小红书）、流媒体（Netflix、爱奇艺）、新闻资讯、UGC 平台。
- **核心价值**：注意力、娱乐、社交连接。
- **当前商业模式**：广告、订阅、内购（IAP）、电商导流。
- **典型壁垒**：内容生态与创作者网络、用户习惯、算法分发能力。
- **Step 2 待研究**：生成式 AI 正在改变"内容生产"成本，但消费端壁垒（生态、习惯）稳固。AI 在这里更多改变**供给侧**，还是会改变**分发与交互形态**（如对话式入口替代信息流）？

### 类别 7：基础设施/平台型（Infrastructure & Platform）

- **定义**：支撑其他软件运行的底层能力。
- **代表产品**：数据库（Postgres、Snowflake）、云计算（AWS、阿里云）、开发平台/ PaaS、安全（身份、防火墙、防泄漏——作为产业的安全产品归在此标签，但安全作为技术维度横切所有类别，详见第 3 节）、可观测性（监控、日志）。
- **核心价值**：提供可靠、可扩展的底层能力。
- **当前商业模式**：按用量（consumption）计费为主。
- **典型壁垒**：规模效应、可靠性声誉、切换成本、生态。
- **Step 2 待研究**：AI 本身需要大量基础设施（训练/推理），这一层是**被 AI 拉动**而非被替代。但"用 AI 运维 AI"（AIOps）会重塑其内部形态。壁垒极高，创业者难入。

### 类别 8：垂直行业型（Vertical Industry Systems）

- **定义**：嵌入特定行业专属流程的软件。
- **代表产品**：医疗（HIS/EMR、微医）、教育（LMS、学堂在线）、农业管理（农管家）、物流 TMS/运输、零售 POS/会员、房地产、法律/财税 SaaS。
- **核心价值**：把行业 Know-how 固化成可复用的系统。
- **当前商业模式**：按席位、按交易笔数、行业定制。
- **典型壁垒**：行业知识深度、合规、与行业上下游的集成、客户关系。
- **Step 2 待研究**：行业 Know-how 是壁垒，但 AI 可能把"通用智能 + 行业数据"变成新的 Know-how 载体。HYP-003 农业 AI 助手、HYP-004 老年人助手、HYP-005 蓝领助手都落在这个类别或其边缘。这是**创业者最可能切入、也最被大厂忽视**的区域（呼应 AGENTS.md 探索方向 2/3/4/7）。

### 类别 9：个人/家庭管理型（Personal & Household Management）

- **定义**：个人与家庭用于组织日常生活的软件。
- **代表产品**：个人记账（随手记、YNAB）、日历/记事（Google Calendar、系统日历）、笔记（印象笔记、Notion）、任务管理（Todoist）、家庭协作（Cozi、FamilyWall、Honeydue）。
- **核心价值**：降低个人/家庭的信息负担与协调成本。
- **当前商业模式**：Freemium、个人订阅（低价）。
- **典型壁垒**：习惯锁定、轻量（竞品易复制）、网络效应弱（家庭小群体）。
- **Step 2 待研究**：家庭是否需要在多个工具间协调信息、这种协调是否高频且代价明确，仍需真实家庭行为证据。AI 能否提供有增量价值的协调层，不能由工具功能清单推断。

### 类别 10：知识与信息获取型（Knowledge & Information Access）

- **定义**：帮用户找到、学习、理解信息的系统。
- **代表产品**：搜索引擎（Google、百度）、知识库/百科（维基、知乎）、在线学习（Coursera、得到）、问答与参考、企业知识管理（Confluence、语雀）。
- **核心价值**：从信息海洋中高效获取所需。
- **当前商业模式**：广告（搜索）、订阅（学习）、企业授权。
- **典型壁垒**：内容/索引规模、用户习惯、品牌信任。
- **Step 2 待研究**：这是被 LLM **直接重定义**的类别——ChatGPT/Claude 本身就是"对话式信息获取"，正在替代传统搜索。知识的可执行化（花叔女娲 Skill 把人物思维变成可调用的知识资产）也诞生于此。对应 VISION.md 的"知识资产"形态。

## 3. Security, Assurance & Trust：横切研究主题

> 本节为 2026-11-10 引入的概念升级：不是在十类标签后追加一个"网络安全"类别，而是引入贯穿全部类别的可信技术研究维度。外部框架引用已于 2026-11-10 逐一核实（见 3.6）；未经证实的推演均已标注为 Agent 生成的分析假设。

### 3.1 研究对象与核心问题

**研究对象**：不只是"哪些公司在卖安全产品"，而是**软件的可信性**。

**核心问题**：我们凭什么相信一个软件真的做了它声称自己做的事情？

这个问题比"谁买防火墙"更根本，因为它触及软件的数学基础、执行机制和信任边界，而且随着 AI Agent 获得自主执行能力，正在从专业领域问题上升为 AI 原生软件的基础设施问题。

### 3.2 四个研究维度

| 维度 | 研究内容 |
|------|---------|
| **Protected Object（保护对象）** | 身份、代码、数据、模型、设备、运行环境 |
| **Security Property（安全属性）** | 机密性、完整性、可用性、真实性、授权正确性、隐私 |
| **Assurance Method（保障方法）** | 数学证明、静态分析、动态测试、审计、来源证明 |
| **Trust Boundary（信任边界）** | 用户、Agent、工具、系统、第三方服务之间的信任关系 |

### 3.3 三层技术分支全景（观察标签，允许交叉，非 MECE）

**第一层：基础理论与核心技术**——技术深度最高、持续产生基础研究价值的区域

1. **密码学与密码协议**（Cryptography）：对称/非对称加密、数字签名、哈希、密钥管理、PKI、零知识证明、多方安全计算、后量子密码学。核心问题：如何在不信任通信环境和参与方的情况下建立可信的身份、机密性和完整性？
2. **形式化验证与数学证明**（Formal Methods）：定理证明、模型检测、形式化规格、协议验证、程序正确性证明。核心问题：能否证明软件在规定条件下确实按预期运行，而不只是通过有限测试？
3. **程序分析与软件验证**（Program Analysis）：静态/动态分析、符号执行、污点分析、模糊测试、代码审计。核心问题：源代码究竟会产生什么实际行为？潜在错误和不安全状态藏在哪里？
4. **操作系统、内核与运行时安全**（Systems Security）：进程隔离、内存安全、虚拟化、沙箱、权限模型、运行时保护。核心问题：程序获得了什么权限？程序间隔离是否真的可靠？
5. **硬件与可信计算**（Hardware Security & Trusted Computing）：安全启动、TPM、可信执行环境、HSM、固件安全、硬件信任根、侧信道防护。核心问题：当硬件本身也可能不可信时，信任从哪里开始？
6. **编程语言、编译器与构建安全**（Language & Compiler Security）：类型系统、内存安全语言、编译器安全、构建工具链、可复现构建、二进制完整性。核心问题：从源代码到最终可执行产物，转换过程中有没有发生未经授权或不可验证的变化？

**第二层：安全工程与产品**——商业市场上可见的安全产业主体（对应类别 7 观察标签）

7. 应用安全（Web/移动/API/安全架构）；8. 身份与访问管理（IAM、零信任）；9. 网络安全（协议、TLS、网络隔离）；10. 云原生安全（容器、K8s、工作负载）；11. 数据安全与隐私工程；12. 软件供应链安全（SBOM、软件签名、构建来源证明）；13. 终端与移动安全；14. 嵌入式与 IoT 安全；15. 工业控制与关键基础设施安全（OT/ICS）；16. AI 与 Agent 安全（模型完整性、数据投毒、工具权限、Agent 身份与执行边界）

**第三层：安全运营与保障**——对应安全生命周期而非纯技术分类（组织框架见 3.6 NIST CSF 2.0）

17. 漏洞研究与管理；18. 安全测试与评估（授权渗透测试、红队/紫队）；19. 威胁情报；20. 恶意软件研究与数字取证；21. 安全监测与事件响应（SOC/SIEM/检测工程）；22. 网络韧性与灾难恢复；23. 安全治理与风险管理（GRC、合规、审计）

### 3.4 七个可信基础与信任链

从第一层的六个分支，加上软件供应链与 AI/Agent 安全，得到技术深度最高、最值得持续投入的七个方向：

| # | 方向 | 一句话定位 |
|---|------|-----------|
| 1 | Cryptography | 信任的数学基础——把信任从社会约定转化为可验证的数学性质 |
| 2 | Formal Verification | 正确性的证明——研究"能证明什么"，而非"测试碰巧发现了什么" |
| 3 | Program Analysis | 软件行为的真实面貌——源代码、运行状态、数据流与实际行为的关系 |
| 4 | Systems Security | 执行环境的真实边界——内存、进程、权限、隔离 |
| 5 | Hardware Root of Trust | 信任的物理起点——硬件、固件与软件之间如何建立可信关系 |
| 6 | Software Supply Chain | 软件来源的真实性——从源码、依赖、构建到发布全程可追溯、可验证 |
| 7 | AI & Agent Security | 自主软件的可信执行——身份、权限、授权、数据边界与责任 |

这七个方向共享一条**信任链**：

```
源代码（我们声明软件应该做什么）
  → 构建过程（源代码如何变成可执行产物）
    → 执行环境（程序实际上在哪里、以什么权限运行）
      → 运行行为（程序实际做了什么）
        → 验证与证据（如何证明行为符合预期）
          → 责任与追溯（谁授权、谁执行、谁承担责任）
```

这条链比普通的功能分类更接近软件可信性的根本问题（3.1 节核心问题）。

### 3.5 AI 时代安全重要性的推演（Agent 生成的分析假设）

> ⚠️ 本节推演为 Agent 基于公开框架与行业讨论生成的**分析假设**，不是实地研究结论。"安全成为 AI 原生软件的基础设施"这一判断需要通过真实的产品事故、企业采购行为、监管动作和开发者实践来验证（可接入 Exploration 0002 的信号检测）。

传统软件的安全边界相对容易描述：用户发出请求，软件按权限执行确定的程序逻辑。AI Agent 改变了这个局面：Agent 可能自主理解任务、选择工具、读取文件、访问外部服务、组合多个系统并执行操作。于是传统安全问题延伸出新的形态（以下对照均为待验证假设）：

| 传统安全问题 | AI Agent 时代延伸出的问题（假设） |
| ------ | ----------------------- |
| 身份认证 | 如何确认 Agent 代表谁执行任务？ |
| 权限控制 | Agent 能否获得恰好完成任务所需的权限（而非过多）？ |
| 数据安全 | Agent 能否区分可信数据与不可信输入？ |
| 软件供应链 | Agent 使用的模型、工具和依赖是否可信？ |
| 执行安全 | Agent 能否在授权范围外产生副作用？ |
| 审计 | 如何完整还原 Agent 为什么执行某项操作？ |
| 系统韧性 | Agent 出错后如何限制影响并恢复？ |

**核心假设**：安全可能从"软件产品的附加功能"转变为"AI 原生软件的基础设施"——Agent 的授权、执行隔离、工具调用审计、数据来源验证和行为证明会成为值得长期研究的技术分支。这与 VISION.md"壁垒从代码转向工作流/数据/集成/信任"的判断相互印证，但两者都尚未获得实证。

### 3.8 研究主题拆分：漏洞研究产业与软件可信度产业

2026-11-10 引入漏洞挖掘行业研究后，本主题进一步拆分为两个视角：

| 研究主题 | 核心问题 | 载体 |
| -------- | -------- | ---- |
| **漏洞研究产业** | 谁能发现软件缺陷？如何验证、披露、定价和分配研究成果？ | 独立框架文档 `vulnerability-research-industry.md`（含产业关系、上报市场运行规则、中国法规合规边界、黑灰产经济作用分析，法规与平台引用已核实） |
| **软件可信度产业** | 如何证明软件符合安全属性？如何持续发现、修复和验证缺陷？ | 本节第 3.1–3.7 内容及七个可信基础方向 |

两个主题共享同一核心问题（3.1 节）：我们凭什么相信一个软件真的做了它声称自己做的事情？漏洞研究产业从"安全性失败时的发现与定价"切入，软件可信度产业从"证明安全性并让它可验证"切入——前者是镜子，后者是正路。漏洞挖掘行业不是在出售"漏洞"，它实际交易的是软件系统中尚未被证明的安全性；黑灰产揭示了安全性失败时的代价，而合法安全行业的工作是把代价转化为可验证、可控制、可修复的技术能力（此判断为 Agent 生成假设，详见漏洞研究产业文档第 4/7 节）。
