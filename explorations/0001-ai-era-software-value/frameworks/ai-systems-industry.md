# AI Systems & Engineering：产业与技术机会图谱

**所属探索**：Exploration 0001 — AI 时代软件价值的初步研究  
**状态**：研究地图与候选问题；尚未验证为市场机会  
**创建日期**：2026-11-10  
**目的**：把 AI 本身作为独立的软件产业和工程研究领域，而不只是影响传统软件的外部技术变量。

---

## 1. 研究边界

Noos Enterprise 同时研究三类对象：

1. **既有软件产业**：AI 如何改变已有产品、行业流程和软件商业模式。
2. **AI 自身产业**：模型、推理、数据、Agent、评估、安全和开发工具链有哪些尚未解决的工程问题。
3. **技术与真实需求的交汇点**：哪些新能力让过去成本过高、效果不可靠或无法自动化的任务出现新的解决可能。

本文件聚焦第二类，并为第三类提供问题候选。

这里的技术地图不是市场规模分类，也不是创业机会排序。某个分支的技术重要性、论文数量、GitHub 活跃度或融资热度，都不能单独证明用户需求、付费意愿或市场空白。

## 2. AI 软件产业的八个观察领域

| 领域 | 覆盖内容 | 核心研究问题 |
|---|---|---|
| 模型与智能能力 | Foundation Models、LLM、SLM、多模态、推理模型、开放权重、训练与后训练 | 如何以可接受的成本获得更可靠、更专业的模型能力？ |
| AI 计算与推理基础设施 | GPU/NPU、模型部署、推理引擎、量化、缓存、批处理、模型路由 | 如何稳定满足延迟、吞吐、容量和成本约束？ |
| AI 数据与上下文工程 | 数据治理、训练数据、RAG、检索、向量索引、知识图谱、Context Engineering、Memory、来源与权限 | 如何让模型使用正确、及时、完整且有权访问的信息？ |
| Agent 与 AI 应用工程 | Agent Runtime、工具调用、编排、状态管理、多 Agent、协议、系统集成 | 如何让模型可靠地完成跨步骤、跨系统任务？ |
| AI 评估、测试与可靠性 | Evals、Benchmark、回归测试、输出质量、在线监控、人工复核 | 如何证明系统在真实任务中持续完成了预期工作？ |
| AI 安全与可信治理 | Prompt Injection 防护、身份、权限、沙箱、模型与数据供应链、隐私、审计 | 如何限制、验证和追溯 AI 的行为？ |
| AI 开发者工具与工程平台 | AI IDE、代码生成、代码审查、测试生成、AI CI/CD、模型/API Gateway、可观测性 | AI 如何改变软件的生产、测试、部署和维护？ |
| AI 垂直应用与专业系统 | 医疗、金融、法律、工业、科研、设计、教育、农业、企业运营 | 哪些专业任务可以重组，哪些仍需专家判断和责任承担？ |

这些领域可以交叉。例如，一个 Agent 审计系统同时涉及 Agent 工程、身份授权、安全和可观测性；不应被强行归入单一类别。

## 3. 技术分支地图

### 3.1 模型与智能能力

- Foundation Models：模型架构、预训练、规模与能力边界。
- Reasoning Models：推理、规划、分解任务和复杂问题处理。
- Small Language Models：小模型、端侧模型、资源受限部署。
- Multimodal Models：文本、图像、音频、视频及跨模态理解。
- Open-weight Models：开放权重模型的部署、适配、维护与许可。
- Post-training：SFT、偏好优化、强化学习、领域适配和模型行为约束。

### 3.2 计算与推理基础设施

- 推理服务、模型 Serving、GPU/NPU 调度。
- 量化、KV Cache、Batching、并发和内存管理。
- 模型路由、Fallback、限流、队列和 Backpressure。
- 延迟、吞吐、可用性、单位任务成本与容量规划。

### 3.3 数据与上下文工程

- 数据清洗、去重、标注、合成数据与数据质量。
- Retrieval、RAG、向量检索、混合检索和重排序。
- Context Engineering、长期/短期 Memory、上下文压缩。
- 数据来源、时效性、版本、权限继承和可追溯性。
- 专业知识库与业务系统之间的数据同步和冲突处理。

### 3.4 Agent 与应用工程

- Agent Runtime、工具调用和执行沙箱。
- 规划、编排、状态持久化与多 Agent 协作。
- 长任务的 Durable Execution、Checkpoint、Idempotency 和恢复。
- 工具/API 协议、身份委派、权限传递和系统互操作。
- Human-in-the-loop、暂停、接管、撤销和补偿操作。

### 3.5 评估、测试与可靠性

- 离线 Evals、在线评估和任务级 Benchmark。
- 版本回归、模型/Prompt/数据/检索器变更比较。
- 质量漂移、失败分类、可复现样本和人工纠正反馈。
- 端到端任务成功率、稳定性、延迟与成本联合评估。
- 评估集污染、测试覆盖不足以及评估标准本身的偏差。

### 3.6 安全与可信治理

- Prompt Injection、不可信输入和数据外泄风险。
- Agent Identity、Delegated Authorization、最小权限和策略执行。
- 工具隔离、运行时沙箱、执行审批与操作审计。
- 模型、数据集、工具和依赖的来源与完整性。
- 隐私、敏感数据处理、责任边界和事件响应。

### 3.7 AI 开发者工具与软件工程

- AI IDE、代码生成、代码理解和代码审查。
- AI 生成测试、测试数据、回归验证和 CI/CD 集成。
- Program Analysis、Static/Dynamic Analysis、Property-based Testing。
- Formal Verification、Mutation Testing 和独立验证。
- 开发环境、构建来源证明、依赖治理和可观测性。

### 3.8 垂直与专业系统

- Domain Adaptation、Fine-tuning、Post-training。
- 专业数据集、任务定义、评估标准和专家复核。
- 行业工作流、法规约束、数据授权和责任承担。
- 模型能力边界、失败转人工以及持续质量管理。

## 4. 七个具体问题候选

以下是值得调查的**问题假设**，不是已经确认的市场需求。每个候选都必须继续调查真实工作流、现有替代方案、发生频率、经济后果、购买者和证伪条件。

### A. 模型、Prompt 与数据变更后的质量回归

- **可能的用户**：AI 产品工程师、质量工程师、模型平台团队。
- **具体工作**：模型、Prompt、工具、检索器或数据版本变化后，重放历史任务，比较输出和任务结果，定位质量退化，并追踪人工纠正。
- **问题假设**：团队可能缺少贯穿真实任务样本、版本差异、质量结果和人工纠正的统一回归流程。
- **证伪问题**：现有 Evals、测试框架和内部平台是否已经低成本解决该问题？模型变化引起的退化是否足够频繁和昂贵？

### B. Agent 身份、授权与操作责任追溯

- **可能的用户**：企业安全团队、IT 管理者、平台工程师、审计人员。
- **具体工作**：确定 Agent 代表谁行动、获准访问什么资源、调用了哪些工具、产生了哪些副作用，以及谁能够批准、暂停或撤销操作。
- **问题假设**：现有 IAM、OAuth、API Gateway 和审计日志之间可能无法完整表达 Agent 的委派身份与执行链。
- **证伪问题**：现有身份和权限体系是否能够通过配置与集成覆盖这些需求？具体缺口是否导致过多人工审批或实际风险？

### C. AI 上下文的质量、时效、权限与来源

- **可能的用户**：数据工程师、知识管理团队、AI 应用负责人。
- **具体工作**：回答问题或执行任务前，判断检索内容是否正确、是否过期、是否互相冲突、是否允许当前用户访问，以及最终结果引用了哪些资料。
- **问题假设**：数据权限、知识新鲜度、来源追溯和检索质量可能分散在多个系统中，难以联合验证。
- **证伪问题**：现有数据目录、文档权限、检索评估和知识管理产品能否充分解决？用户是否会为更完整的上下文证明付费？

### D. Agent 长任务的可靠执行与恢复

- **可能的用户**：Agent 应用工程师、平台工程师、业务运营负责人。
- **具体工作**：任务跨越多个系统时，处理中断、超时、重复调用、结果不确定、人工接管和安全恢复。
- **问题假设**：长任务的状态、步骤结果、幂等性和补偿操作可能缺少统一且可审计的表示。
- **证伪问题**：现有工作流/Durable Execution 系统是否已经满足需求？问题是否只出现在少数复杂场景？

### E. 推理容量、成本与质量的协调

- **可能的用户**：AI 基础设施团队、平台团队、AI 产品工程师。
- **具体工作**：在成本预算、延迟、容量、限流和任务质量约束下协调模型调用、路由、重试和降级。
- **问题假设**：模型供应商与模型规格变化可能使团队难以稳定控制单位任务成本和服务质量。
- **证伪问题**：供应商能力、现有 Gateway 和自建观测能否充分解决？优化带来的节约是否超过运维复杂度？

### F. AI 生成代码的独立验证

- **可能的用户**：软件工程团队、安全工程师、质量平台团队。
- **具体工作**：用独立于代码生成假设的方式检查程序行为、安全属性、边界条件、依赖和构建产物。
- **问题假设**：生成代码和生成测试可能共享错误假设，常规测试未必能发现语义层面的缺陷。
- **证伪问题**：现有 CI、静态分析、代码审查和测试体系是否已能以可接受成本覆盖？新增验证是否显著减少线上缺陷或审查成本？

### G. 专业领域数据与能力评估

- **可能的用户**：医疗、金融、工业、法律、科研等专业机构的 AI/数据团队。
- **具体工作**：定义专业任务标准，维护合法可用的数据集和评估样本，判断模型更新是否影响专业能力，并设计专家复核和转人工边界。
- **问题假设**：通用 Benchmark 可能无法代表专业任务，机构可能需要自己的任务级评估与质量治理能力。
- **证伪问题**：现有专业服务、模型厂商或内部团队是否已满足需求？领域数据治理成本是否高于可获得的收益？

## 5. 优先深入的三个研究主题

以下是研究议程，不是商业价值排名：

1. **AI 系统可靠性与验证**：模型能回答，不代表系统能正确完成任务。研究 Evals、回归验证、质量漂移、可复现失败和人工纠正。
2. **Agent 与现实世界的权限和责任边界**：研究身份、授权、工具调用、审计、接管与撤销，连接 IAM、安全和企业治理。
3. **专业知识如何转化为可靠的 AI 能力**：研究领域数据、任务标准、专业评估、模型适配以及专家责任。

## 6. 基础模型研究价值与产品切入条件

基础模型训练、先进推理、GPU 计算和芯片研发具有重要技术价值，但其资本、人才、算力和周期门槛可能很高。Noos 应允许形成“值得长期跟踪，但当前没有合适产品切入点”的结论。

机会筛选至少要分开回答：

- 技术问题是否真实、重要且尚未解决？
- 哪类组织或个人正在承担问题成本？
- 目前通过什么工具、人工流程或外部服务解决？
- 问题出现的频率和损失是否足够明确？
- 谁拥有采购权、预算或改变流程的能力？
- 新技术是否真正改善结果，而非只降低 Demo 成本？
- 是否存在现成方案足以满足需求？

## 8. 研究纪律

- 论文、GitHub Star、社区讨论、融资和标准活动都是**技术或产业信号**，不能单独证明用户需求。
- 产品假设必须回到具体用户、具体任务、当前替代方案、真实成本和购买决策。
- Agent 生成的分支地图、候选问题和优先主题均应标记为研究假设。
- 对外访谈、用户招募、个人信息收集、付费服务和公开部署，遵守仓库 AGENTS.md 的明确授权规则。
- 不为填满地图而强行创建产品假设；没有证据时记录“不确定”或“不值得继续”。
