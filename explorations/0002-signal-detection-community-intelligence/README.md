## 1. 探索目标

### 1.1 核心问题

**如何从技术变化、工程实践和产业活动中发现值得深入研究的领域，并进一步判断这些变化是否对应真实、重复发生的用户问题？**

传统的信息收集方式（新闻订阅、社交媒体关注）只能获取已经传播开的信息。当信息到达主流渠道时，早期机会窗口已经关闭。我们需要的是：

- **技术信号**：观察模型能力、推理基础设施、Agent、数据/上下文、评估、安全、软件工程和传统软件领域的变化。
- **工程信号**：观察开源项目维护活动、缺陷、迁移、性能与可靠性讨论，以及公开标准和事故信息。
- **问题线索**：从反复出现的失败、替代、人工补救和成本抱怨中形成待调查的问题线索。
- **反馈循环**：把技术信号映射到研究领域和技术分支，再形成 Problem Brief；最终是否构成需求必须由真实工作流和行为证据检验。

### 1.2 与 Exploration 0001 的关系

Exploration 0001 建立了软件产业分类图谱（`frameworks/software-landscape-taxonomy.md`），但这是静态快照。信号检测系统为其提供**动态更新机制**：

- **动态更新**：为传统软件领域和 AI & Model Systems 提供技术与工程变化线索。
- **领域扫描**：发现信号后，先定位研究领域和技术分支；不能直接据此判断存在市场机会。
- **问题转化**：只有进一步找到具体使用者、任务、现有替代方案、反复摩擦和经济后果，才能形成机会假设。

---

### 当前技术覆盖范围与证据边界

当前采集脚本覆盖 arXiv、GitHub 和 Hacker News。配置已扩展为观察 AI 模型与 Agent、推理、RAG/评估、网络安全、软件供应链、静态分析、形式化方法、数据工程、分布式系统、开发者工具和可观测性等技术分支。

- arXiv 类别和 GitHub Topic 是采集过滤条件，不是对整个领域的完整覆盖。
- GitHub Star 反映平台关注度，不等于持续使用、采购或收入。
- arXiv 论文数量反映研究活动，不等于可用产品或市场需求。
- Hacker News 讨论反映技术社区表达，不代表普通用户或采购者意见。
- arXiv API 本身不提供引用列表；引用异常检测在接入独立引用数据源前不能视为完整能力。
- 当前还没有接入 Crunchbase、Product Hunt、招聘、采购或真实用户行为数据。

**核心规则：信号只能提出“值得进一步调查”的问题，不能直接被标记为产品机会。**

## 2. 方法论框架

本探索采用四层架构，从数据采集到决策支持形成闭环：

```
┌─────────────────────────────────────────────────────────┐
│  Layer 4: 反馈循环层                                      │
│  - 预测准确性追踪                                         │
│  - 决策质量评估                                           │
│  - 方法论迭代优化                                         │
└─────────────────────────────────────────────────────────┘
                           ↑
┌─────────────────────────────────────────────────────────┐
│  Layer 3: 实践参与层                                      │
│  - 社区贡献（PR、技术博客、问答）                          │
│  - 关系建立（与关键人物互动）                              │
│  - 声誉积累（成为可信成员）                                │
└─────────────────────────────────────────────────────────┘
                           ↑
┌─────────────────────────────────────────────────────────┐
│  Layer 2: 社区结构分析层                                  │
│  - 社会网络分析（SNA）                                    │
│  - 关键人物识别（意见领袖、信息枢纽、新兴声音）            │
│  - 跨社区传播路径追踪                                     │
└─────────────────────────────────────────────────────────┘
                           ↑
┌─────────────────────────────────────────────────────────┐
│  Layer 1: 信号检测层                                      │
│  - 数据源接入（arXiv、GitHub、Hacker News 等）            │
│  - 弱信号识别（引用网络变化、低星 trending、放弃叙事）     │
│  - 主题建模与变化点检测                                   │
└─────────────────────────────────────────────────────────┘
```

### 2.1 Layer 1: 信号检测层

**目标**：在信息成为主流之前捕获弱信号

**数据源分层**：

| 数据层 | 当前来源 | 可观察内容 | 状态 |
|------|----------|----------|------|
| 学术研究 | arXiv API | 论文元数据与技术主题；引用关系需额外来源 | 已接入 |
| 开源工程 | GitHub REST API | 项目元数据、低星项目、Star 时间序列 | 已接入 |
| 技术讨论 | Hacker News Firebase API | 帖子与评论中的问题、迁移和讨论线索 | 已接入 |
| 市场与采购 | Crunchbase、Product Hunt、招标与招聘 | 融资、新产品、采购和岗位需求 | 规划中，当前脚本未接入 |
| 专业用户行为 | 经授权的访谈、观察或使用记录 | 实际任务、替代方案、成本与购买行为 | 需要人类明确授权 |

**弱信号识别方法**：

1. **引用网络变化检测**
   - 监控 arXiv 论文引用网络的结构性变化
   - 工具：NetworkX（图分析）、变化点检测算法
   - 信号示例：某篇论文突然被多个不相关领域引用

2. **低星项目 trending 分析**
   - 监控 GitHub 上 10-100 星项目的增长率异常
   - 工具：GitHub API、trending 追踪脚本
   - 信号示例：某项目一周内从 20 星增长到 200 星

3. **"放弃叙事"检测**
   - 监控技术博客、Stack Overflow 中"放弃 X 工具"类文章
   - 工具：文本分类（BERTopic）、关键词匹配
   - 信号示例：多个独立博客同时发布"从 X 迁移到 Y"文章

4. **小众论坛重复话题**
   - 监控 Reddit、Hacker News 中重复出现的主题
   - 工具：主题建模（LDA/BERTopic）、频率统计
   - 信号示例：某话题在 3 个不同 subreddit 中一周内出现 5+ 次

### 2.2 Layer 2: 社区结构分析层

**目标**：描述公开协作、项目主题和讨论结构，辅助定位值得阅读的项目与技术讨论。中心性指标、Topic 共现和时间先后关系，不等于真实影响力或因果传播。

**社会网络分析（SNA）维度**：

1. **关键人物识别**
   - **意见领袖**：高影响力节点（PageRank、Betweenness Centrality）
   - **信息枢纽**：连接不同社区的桥接节点
   - **新兴声音**：近期活跃度快速上升的节点

2. **社区结构分析**
   - **社区检测**：Louvain、Label Propagation 算法
   - **跨社区传播**：追踪信息从一个社区到另一个社区的路径和时滞
   - **信息时滞测量**：信号从学术层传播到市场层的时间

3. **工具与方法**
   - **NetworkX**：图构建和分析
   - **Gephi**：可视化（可选，用于报告）
   - **节点中心性指标**：Degree、Betweenness、Closeness、PageRank

### 2.3 Layer 3: 实践参与层

**目标**：在明确授权后，把公开资料研究与现实工程实践连接起来。社区参与是可选研究方法，不是产品需求证据，也不是以 Agent 声誉积累为目标。

**参与策略**：

1. **技术贡献**
   - 提交 PR（修复 bug、添加功能、改进文档）
   - 开源自己的工具（信号检测脚本、数据可视化工具）
   - 目标：在 3 个核心社区建立可见度

2. **知识贡献**
   - 撰写技术博客（分析方法论、工具使用经验）
   - 回答 Stack Overflow 技术问题
   - 在 Reddit/Hacker News 参与讨论

3. **关系建立**
   - 与关键人物互动（评论、转发、合作）
   - 参与社区活动（线上/线下 meetup）
   - 目标：成为可信成员，获得内部信息

**使用边界**：PR、博客、评论、活动参与等任何对外行为均须遵守 AGENTS.md 的授权要求，并明确 Agent 身份。参与次数、声誉和被提及次数不作为产品机会成功标准。

### 2.4 Layer 4: 反馈循环层

**目标**：追踪预测准确性，迭代优化方法论

**追踪指标**：

1. **信号质量**：按信号类型统计已确认与已否定样本，明确未决样本，不把未决信号计入准确率分母。
2. **提前量**：只有具备可比较的外部时间基准时，才计算信号发现时滞。
3. **问题转化率**：记录信号是否进入具体 Problem Brief，以及是否找到使用者、任务、现有替代方案和成本证据。
4. **现实验证状态**：明确区分公开资料推断、观察到的行为、真实用户反馈、使用结果和实际付费。
5. **方法论回测**：在历史样本和预先定义的判定标准上回测；在有足够样本前不设定“70% 准确率”之类的成功承诺。

社区参与数据只用于描述研究活动，不计入机会验证质量。

## 3. 数据源与技术栈

### 3.1 数据源清单

| 数据源 | API/访问方式 | 数据内容 | 采集频率 | 优先级 |
|--------|--------------|----------|----------|--------|
| arXiv | arXiv API | 论文元数据、引用关系 | 每日 | P0 |
| GitHub | GitHub REST/GraphQL API | 项目元数据、star 历史、PR/Issue | 每日 | P0 |
| Hacker News | Firebase API | 帖子、评论、投票 | 每日 | P0 |
| Stack Overflow | Stack Exchange API | 问题、标签、投票 | 每周 | P1 |
| Reddit | Reddit API | 帖子、评论、subreddit 数据 | 每日 | P1 |
| Twitter/X | Twitter API v2 | 推文、用户、话题 | 实时/每日 | P2 |
| Crunchbase | Crunchbase API | 融资事件、公司信息 | 每周 | P2 |
| Product Hunt | GraphQL API | 新产品、投票、评论 | 每周 | P2 |

### 3.2 技术栈

**数据采集**：
- Python（requests、aiohttp）
- API 客户端库（arxiv、github3.py、praw）

**数据分析**：
- NetworkX（图分析）
- scikit-learn（聚类、分类）
- BERTopic（主题建模）
- pandas、numpy（数据处理）

**可视化**：
- matplotlib、seaborn（静态图表）
- plotly（交互式图表）
- Gephi（网络可视化，可选）

**存储**：
- SQLite（本地数据存储）
- JSON/CSV（导出数据）

## 5. 权限边界对齐

根据 `AGENTS.md` 的权限边界，本探索的操作范围：

**可自主执行**：
- 采集公开数据（arXiv、GitHub、Hacker News、Stack Overflow、Reddit）
- 浏览公开网站和技术博客
- 本地构建原型和分析脚本
- 分析公开的技术文档和论文

**需人类授权**：
- 联系真实用户进行访谈
- 在社区中以真实身份发言（提交 PR、发布博客）
- 购买付费 API 服务（如 Twitter API 高级计划）
- 部署公开产品或服务

**当前阶段策略**：
- 优先使用免费 API 和公开数据源
- 本地构建原型，验证方法论
- 社区参与部分需人类授权后执行
